# DBChangeLogger（C# / Windows）

PostgreSQLとSQL Serverで同じ操作を行い、操作前後の追加・更新・削除を比較するツールです。どちらかのDBで変更があった主キーについて、両DBの操作後の行をExcelに貼り付けられます。DBごとに行をまとめて表示し、片側が未変更なら「変更なし」としてレコード値を空欄にします。両DBとも変更なしの主キーは出力しません。専用の「主キー」「時点」列は出力しません。DB本来のidなどの取得列を表示し、削除行では主キーだけ残し、その他の値は「〈行なし〉」にします。エビデンスブックにマクロは不要です。

## 実行方法

初めて使う方は **[導入手順](INSTALL.md)** を読んでください。作成者の接続設定・ビルド・社内配布と、利用者の起動・Excel保存を順番に説明しています。

GitHubの公開Releaseは**DB接続なしの確認用ビルド**です。通常起動では取得できません。画面・出力を確認するときは `DBChangeLogger.exe --demo` で起動します。実際の接続情報と `connections.enc` はGitHubへ公開せず、設定済みZIPは社内だけで共有してください。

1. Windows配布ZIPを展開し、同じフォルダの `DBChangeLogger.exe` を起動します（Windows x64、.NET 9ランタイム同梱・別途インストール不要）。DLLと connections.enc を含むフォルダ全体を保持してください。
2. 接続先は作成者がソースで設定します。利用者は接続情報を入力せず、同梱の暗号化設定から同じDBへ直接接続します。Windows認証は必須ではありません。
3. スキーマはPostgreSQL public / SQL Server dboに固定です。起動時に両DBを読み取り、共通テーブルを「テーブル一覧」に表示します。テーブル名の部分一致で一覧を絞り込めます。テーブルを選ぶと列定義を読み込みます。取得列・除外列は「列を選択」の検索付きチェック一覧から指定し、未指定なら全列を取得します。主キー列は取得列へ自動追加します。比較・Excel出力は取得列が対象です。主キーはDBの定義から自動取得します。存在しない列や片方だけにある列は候補に含めません。検索列も候補から選びます。「テーブル一覧を再読込」で一覧を更新できます。検索条件は最初1行で「＋ 条件を追加」「削除」により増減できます。2行目以降の先頭でAND／ORを選び、直前までの条件へ結合します。AND／ORの混在に対応し、SQLの規則でANDをORより先に評価します（A OR B AND C は A OR (B AND C)）。検索列が空欄の行は使わず、全行空欄なら全件を対象にします。
4. 「操作前を取得」を押します。両DBで条件に一致する実件数を確認・表示してから取得します。件数が多くても自動で中断しません。取得後は設定を固定します。
5. 両システムで同じ操作を行い、コミット・非同期処理完了を待ちます。
6. 「操作後を取得・比較」を押し、サマリーを確認します。
7. 「エビデンスをコピー」を押し、Excelの貼り付け先セルで Ctrl+V を押します。Excel専用のSpreadsheetML形式を使い、全セルを文字列型・文字列書式で貼り付けます。先頭ゼロ、日付に見える値、長い数字、指数表記、数式に見える値、前後の空白も保持します。「値のみ」「テキストのみ」は使用しないでください。型を失う形式への自動変換は行いません。
8. Excelブックを `.xlsx` で保存します。

次のテストケースでは「操作前を取得」で取り直せます。テーブルを変更するときは「設定・取得結果をリセット」を押します。接続先の変更は作成者が設定ソースを変更し、配布ZIPを再作成します。終了時と取得・比較処理の完了時に、入力設定・操作前スナップショット・比較サマリー・コピー用エビデンスを保存し、次回起動で復元します。保存先は `%LOCALAPPDATA%/DBChangeLogger/session.bin` です。データは圧縮し、Windowsユーザー固有のDPAPIで保護した鍵を使って暗号化・改ざん検証します。配布フォルダーには保存せず、他PC／別ユーザーへは引き継げません。保存・復元中は進行表示を出します。大量データの保存・復元にはディスク容量と時間が必要です。接続設定が変わった場合は入力だけを復元し、取得データ・比較結果は再利用しません。多重起動は同じWindowsセッションで防止し、再起動操作は既存画面を表示します。強制終了中の未保存の入力や途中の取得データは復元しません。コピー済みエビデンスはクリップボードに残ります。

## 作成者の初回準備

.NET SDK 9.0がある開発PCで次の手順を実行します。利用者のPCにSDKは不要です。

1. `Configure/PrivateConnections.local.cs` の `Postgres` と `SqlServer` に接続文字列を入力します。ソースZIPから展開した場合は、`PrivateConnections.example.txt` を同名の `.local.cs` としてコピーしてください。
2. PostgreSQLはHost、Database、Username、Password、SQL ServerはServer、Database、User ID、Passwordを指定します。TLS関連の値は既存のDB環境に合わせます。例はテンプレートのコメントにあります。C#文字列の引用符・バックスラッシュはエスケープしてください。
3. PowerShellでソースフォルダーを開き、`./Publish.ps1` を実行します。設定を検証・暗号化してからWindowsアプリと配布ZIPを作ります。接続文字列をコマンド引数へ渡す必要はありません。
4. `artifacts/DBChangeLogger-Windows-x64.zip` を共有します。利用者は展開し `DBChangeLogger.exe` を起動するだけです。接続設定の手入力や管理者権限によるインストールは不要です。

配布物は `DBChangeLogger.exe`、`Microsoft.Data.SqlClient.SNI.dll`、`connections.enc`、説明書です。設定ファイルを単体で失わないよう、フォルダー全体を配布してください。設定未入力・形式不正なら配布処理は失敗します。既存ZIPは更新されないので、以前のZIPを誤って配らないよう成功メッセージを確認してください。

接続情報未入力で画面だけを確認する場合は `./Publish.ps1 -DemoOnly` を使い、`DBChangeLogger.exe --demo` で起動します。このZIPには接続設定がありません。通常起動では設定不足を表示し取得を無効にします。

通常のDBユーザー・パスワード認証を使えば、ツールのためのSSPI/Kerberosや中継サーバーは不要です。既に使えるDBアカウント、対象テーブルのSELECT権限、各PCからDBへのネットワーク到達性が必要です。DBがパスワード認証を許可していない場合や、ネットワーク・証明書の準備がない場合はDB管理者側の対応が必要です。

SQL ServerのWindows認証を使う場合は `Integrated Security=True` も設定できます。その場合は利用者自身のWindowsアカウントの権限で接続します。ツールが作成者のWindowsアカウントに成り代わることはありません。

## 表示と判定

- 黄色: 操作前後で変わったセル。追加・削除は除外列以外が対象。
- 赤色: 両DBで変更列または変更前後の値が異なるセル。
- 追加の操作欄は緑色、削除は灰色。
- 片方だけ変わった主キーも両DBの行を出力します。DBごとにまとめて表示し、もう片方は「変更なし」としてレコード値を空欄にします。
- 両DBで操作種別・変更列・変更前後の値が一致したとき「一致」。変更列の変更前値が既に違っていた場合も「不一致」。変更していない列の既存の差だけでは不一致にしません。
- Excelの「判定」列は設けず、表の末尾へ全レコードをまとめた「判定」行を1行だけ表示します。ある列に不一致が1件でもあれば×です。一致・変更なしは◯（グリーン）、不一致は×（赤色）、除外列は除外と表示します。
- 除外列だけが変わった行は出力しません。
- エビデンスの先頭行には対象テーブルと検索条件だけを表示します。取得列・除外列の行はそれぞれ指定がある場合だけ出力します。取得列は自動追加した主キー列も含めた実際の列一覧を表示します。
- NULL、空文字、存在しない行を別の表示にします。改行・タブは `\n` / `\r` / `\t` で表示します。
- 日時は7桁精度、decimalは末尾ゼロを正規化して厳密比較します。タイムゾーン付き日時はUTC化します。精度の許容差や採番IDの対応付けは未実装です。
- 主キーはDBの定義から自動取得します。複合主キーの定義順が両DBで違っていてもPG側の順に対応付けます。主キーがない／構成が違うテーブルは理由を表示して取得を無効にします。テーブル名は大文字小文字を区別せず対応付け、それだけが異なる複数テーブルがある場合は曖昧な候補を除外します。ビューは対象外です。存在しない列、NULLキー、重複キー、主キーの除外を拒否します。DB間で列順が違っても列名で対応付けます。列名は大文字小文字を区別しません。

## 大きなテーブル・件数表示・中断

- 条件行ごとに検索列・条件（= / >= / <= / 範囲）・値の型・値を指定します。複数行は行ごとのAND／ORで結合します。ANDがORより優先されます。括弧による任意のグループ化は未対応です。検索列は取得列に含まれていなくても使用できます。例: 検索列 id、条件 範囲、型 整数、値 1000、上限 2000。DB側で絞り込み、値はパラメーターとして渡します。検索列に適切なインデックスがあると検索・件数確認の負荷を減らせます。ツールがインデックスを自動作成することはありません。
- 型の表示は文字列／数値だけで、検索列の定義から自動設定します。整数・小数・日時・GUID・真偽値はDBの型へ変換し、値はパラメーターとして渡します。文字列列の先頭ゼロは保持します。日時は `yyyy-MM-dd` または `yyyy-MM-dd HH:mm:ss`、タイムゾーン付き日時は `2026-10-07T09:00:00+09:00` のように入力します（未指定のオフセットはUTC扱い）。真偽値は true/false または1/0です。配列・バイナリなど検索変換未対応の列は検索候補から除外します。
- 条件を空欄にすれば全件を比較できます。条件を指定した場合はその範囲内の差分です。条件列の更新で範囲に出入りした行は範囲内での追加・削除として見えます。
- 取得前に `COUNT(*)`（SQL Serverは `COUNT_BIG(*)`）で両DBの実件数を表示します。百万件を超えても省略・下限表示・自動停止はしません。件数確認自体が全走査になることがあります。その間も処理内容と中断ボタンを表示します。
- 取得中は1万件ごとに取得済み件数を更新します。比較後はPG／SQL Serverの操作前・操作後それぞれの実取得件数を表示します。件数確認と取得は別クエリなので、途中に他の処理が更新した場合は数が変わり得ます。最終表示は取得したスナップショットの件数です。
- 「中断」は件数確認・取得・比較・表生成中に使用できます。キャンセルはDBドライバー／処理ループへ通知します。DBの応答や解放処理に時間がかかる場合は即時終了できるとは限りません。中断後は条件を調整し、操作前から再取得します。
- 比較は全件の行コピーと主キーソートを避け、変更主キーのみをソートします。大量行ではPGとSQL Serverの走査を最大2並列で実行し、列位置は行ループの外で計算します。操作後の変更なし行は操作前のメモリを共有し、Excel用の表もXMLを直接生成して余分なHTML・テキスト・XMLツリーを保持しません。処理はUIとは別スレッドで実行します。
- 数百万件でも必要なメモリは列数・文字列長に依存します。全スナップショットをディスクへ退避する方式ではありません。十分なメモリがないPCでは検索範囲を絞ってください。DB読み取りと通信は全件分必要で、比較処理の高速化だけではその時間をなくせません。

MSTestで300万行×16列・変更3000キーの旧実装との比較を測定します。測定にはDB取得・スナップショット保持量・Excel貼り付けを含みません。測定結果は `artifacts/performance-3000000.txt` を参照してください。

```powershell
$env:EVIDENCE_RUN_PERFORMANCE = '1'
$env:EVIDENCE_PERFORMANCE_ROWS = '3000000'
$env:EVIDENCE_PERFORMANCE_REPORT = "$PWD/artifacts/performance-3000000.txt"
dotnet test Tests/Tests.csproj -c Release --filter "TestCategory=Performance"
```

## 1億件の分割比較ベンチマーク

`Tests/LargeTableTests.cs` の `MeasureOneHundredMillionDistinctKeysInBoundedBatches` は100万件×100バッチ、合計1億件の異なる操作前主キーを実際に比較します。各バッチではPGとSQL Serverの前後4つの論理スナップショットを比較し、合計400百万の論理レコードを対象にします。DB間では同じ読み取り専用の辞書を使い、操作後の行配列は操作前とは別のものを生成して行参照一致の省略を避けます。各セルの同値文字列は共有します。

16列、更新1000件・削除1000件・追加1000件。各バッチで差分の件数・操作種別・一致判定を検査し、比較合計時間、データ生成時間、比較中の割り当て量、テストプロセスのピークメモリを記録します。比較後の差分はバッチ単位で破棄します。主キーは全バッチで異なり、単一バッチの時間からの外挿ではありません。

これは比較エンジンの分割実測です。DB取得・COUNT・通信・ディスクへの分割保存や全体の差分結合・Excel出力・1億件を同時保持するメモリは対象外です。アプリにDB取得を自動分割する機能はまだなく、16GB PCでUIから1億件を全件保持して処理できることを示す測定ではありません。

```powershell
$env:EVIDENCE_RUN_HUNDRED_MILLION = '1'
$env:EVIDENCE_HUNDRED_MILLION_REPORT = "$PWD/artifacts/performance-100000000-after.txt"
dotnet test Tests/Tests.csproj -c Release --filter "TestCategory=HundredMillion" --logger "console;verbosity=detailed"
```

改善前後の実測は `artifacts/performance-100000000-before.txt` と `artifacts/performance-100000000-after.txt`、条件と評価は `BENCHMARK-100M.md` に記録します。実行中の進捗は指定したレポートパスに `.progress` を付けたファイルへ1000万件ごとに保存します。

## 現時点の範囲

1回につき1テーブルの検索条件に一致する行を取得し、メモリ上に保持します。検索条件は複数列の一致・以上・以下・範囲（両端を含む）をAND／ORを混在させて結合できます。一括処理・履歴保存は未実装です。結果がないときは画面下部の表を非表示にし、条件行数に合わせて画面の高さを調整します。取得時はSerializableトランザクションを使うため、SQL Serverで更新処理を待たせる可能性があります。両DBを同時に確定する分散スナップショットではありません。取得中は他の利用者・ジョブによる更新を止めた検証環境で使用してください。

エラー時は機密情報の露出を避けるため、接続先などを含む例外本文を表示しません。

## 接続情報の扱い

接続文字列はAES-GCMで暗号化し、起動時にメモリ上で復号します。画面・ログ・エビデンスには出力しません。暗号化設定を別PCへコピーして利用でき、利用者の入力は不要です。設定ファイルの破損・改ざんは認証タグで検出します。

復号鍵はアプリ側に含まれるため、EXEや共有ソースの解析、プロセスメモリの調査で接続情報を取得することは可能です。平文ファイルを開いて見えてしまうことを避ける、社内数人での簡易的な秘匿です。接続先は通信からも分かり得ます。

`Configure/PrivateConnections.local.cs` と `Configure/bin`・`Configure/obj` には平文の接続情報が含まれます。これらを共有しないでください。Publish.ps1のソースZIPは許可したファイルだけを収録し、実設定ソース・ビルド成果物・暗号化設定を除外します。ソースフォルダー全体をそのままZIP化しないでください。

通常の `Publish.ps1` は暗号化設定の生成前に、両DBへの接続とテーブル一覧の読み取りを確認します。各DBで最大30秒、どちらか失敗したら既存設定と配布ZIPを更新しません。接続情報を含み得る例外本文は表示しません。`-DemoOnly` はDBへ接続せず確認用ビルドを作ります。作成者PCで成功しても、利用者PCのネットワーク・Windows認証の権限は別途確認してください。
